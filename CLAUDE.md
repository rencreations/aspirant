# Project rules

**New session? Read `docs/HANDOFF.md` first** (what the project is, how the owner works, the machine's quirks, the systems, the known caveats), then `docs/HISTORY.md` for why things are as they are. Probes for checking a running site are in `scripts/qa/probes/`.

The Aspirants: a static, immersive Next.js site for the Aspirant story series. Read `README.md` and `docs/design/` first. These rules apply to every change.

## Loading: everything goes in the progress bar

The first loading screen and every page transition report real work. Keep it that way.

- Anything a page needs on first paint is declared in `apps/web/src/lib/route-preloads.ts` as a `PreloadItem` (an image, a data file, a lazy code chunk, fonts). The loading bar, its label and the preloading all come from that list.
- When you add an asset, a lazy chunk or a data fetch that matters at first paint, add it to the list for that route. If it is not in the list, it is not in the bar and the page will pop in late.
- Pre-load for speed: warm the cache before the page opens. Items run in parallel, share a cache, and wait as long as the connection needs. An item that the page does not show until the visitor asks (the other pages' clips, the shorts, the trailer, the voice lines of Selena's and Obsidia's pages) is `deferred`: the bar does not wait for it, it keeps downloading in the background once the page is open, in order of `priority` and behind anything urgent, and the button that needs it shows its loading state until it has arrived. Only the first screen is waited for: the welcome, the idle loop, the buttons, the music and the page the visitor landed on.
- A component with a slow first paint (a WebGL scene) calls `expectReady(id)` from `lib/page-ready.ts` and marks itself ready once it shows something, so the curtain waits for it.
- Big media (the Selena videos, skill clips, trailer, music) is loaded whole into memory through `lib/media-store.ts` by a `PreloadItem` that reports the bytes received, so the bar is real, and it is saved in the browser (Cache Storage) so the next visit does not download it again. Small files read as bytes (data, voice lines) use `cachedFetch`. Replacing a file under the same address means bumping the cache name in `media-store.ts`. Her page and its three pages (`/character/selena/{about,skills,gallery}/`) share one list. Obsidia's page and her three pages (`/character/obsidia/{about,skills,gallery}/`) do the same.
- Never fake progress. Never add a timer that pretends to load.
- **One version only. A slow connection waits behind the loading screen** (owner decision, 1 Nov 2026). There is no lite or cut version of the site, and no time after which a page opens with part of its files. The first loading screen and every page change wait for the whole waited list, however long it takes. The screen says the connection is slow after 15 seconds (`SLOW_AFTER_MS` in `components/loader-gate.tsx`) and then shows the real percentage and bytes received. There is no "Enter now" button, no cap on the first visit, on an item or on a page change, and no per-item `timeoutMs`. Never add one.
- A download that stalls (no byte for 20 seconds, `STALL_MS` in `lib/media-store.ts`), drops, fails with a server error or ends short of the length the server gave is started again after a short wait (1 s growing to 10 s, `lib/retry.ts`), for as long as it takes. Pictures, data, voice lines and code chunks do the same through `lib/preload.ts`. The only item that is skipped (and logged) is one the server says is gone (HTTP 404 or 410) or a picture that arrives whole and cannot be decoded five times: nothing can fix those, and one missing file must not hold every visitor for ever.
- Offline, the loading screen keeps waiting, says so ("Offline. Waiting for the connection."), and goes on by itself when the connection returns. A page change that is already running waits the same way. A click on a page that was never opened, while offline, still shows the calm notice (`components/offline-notice.tsx`) and does not start. A stale tab that asks for a file of an old deploy reloads once (`lib/chunk-guard.ts`), never in a loop and never while offline.
- Before the scripts have started, the cover painted by the boot script in `app/layout.tsx` (`.gate-cover`, with its own notes) stays up: the plain server text of the page is never shown to a visitor, whose connection is slow or not. No timer lets it go. Its only exit is the "Reload the page" link it shows after 90 seconds, for a visitor whose scripts have really failed. `/character` has the same rule for its black cover (`roster-cover.tsx`); only a visitor without JavaScript has it hidden (a noscript rule).
- Never let a progress callback move the curtain after the page has started to open: the curtain's `setBoot` must only overwrite its own bar.
- Waited means the first screen and everything that animates or shows on the sections near the top of the page (small pictures, the autoplaying muted clips of the first sections, the music). Only what the visitor must ask for stays `deferred`: the long films, full size art, the room, the other pages' clips and the voice lines. A page whose deferred item is not there yet when the visitor asks shows the button in its loading state, never a different page.
- A page that is not ready 500 ms after a navigation shows the loading state of the logo transition. Do not remove that.

## One version

There is exactly one version of the site, the full one. It is the same on every device and every connection. There are no performance levels, no lite or balanced mode, no governor that steps effects down, no `?quality` switch, no `<html data-perf>`, and no choice of a smaller video because of the device, the memory, data saving or the speed of the link. The site also ignores the operating system's `prefers-reduced-motion` and has no "Reduce motion" toggle and no `<html data-motion>`. This is the owner's decision (1 Nov 2026). The trade-off is that a visitor who asks their system for less motion still gets the motion. A slow connection or a weak device waits behind the loading screen until everything is loaded, and is never given less. Do not add a reduced, lite or fallback variant of any effect, video or scene (the plain no-WebGL fallback of a scene, a failed download and a browser that cannot play a file are not versions, they are failures to be handled).

## Performance

The site must not lag on an ordinary laptop. Read `docs/design/performance.md`. The rules that matter every day:

- Never write a CSS custom property or an inline style on `<html>` or `<body>` per frame (it restyles the whole page), and never give an element an attribute that a script then selects by. A test guards the cursor.
- Animate `transform` and `opacity` only. No `width`, `left`, `top` or `margin` in an animation. No `filter`, `backdrop-filter` or `mix-blend-mode` over the live picture or on an element with animated children. No per-frame SVG attribute writes.
- A transition between two sections of a long page (Vexana's page) is made by the layout, not by an overlay that appears over the next section for no reason: the section holds its last screen, then a scene plays by itself and the page jumps to the next section while the screen is covered (or the next section simply rises over it, or a heart of colour closes on it as the visitor scrolls). There is no scroll indicator of any kind in a transition. The sections 05 to 09 (the stream, the interactive drama, the 3D process, the gallery and the fanart) have no transitions at all: they follow each other as one plain, smooth scroll, each arriving with its own reveals, and nothing covers the page. The join in front of the stream (the comic) and the ones after the fanart keep their scenes. A lower join works both ways: the next section has no threshold when you arrive by scrolling down, and has one when you scroll up out of it (the same scene plays back). A stop inside a transition snaps one second after the last input (half or more goes on, less goes back), so nobody is left standing in one. While a timed scene plays the scroll is locked (`seams/scroll-lock.ts`) and it is given back only when what arrived is in view and can be used, so nobody scrolls past a heading by accident. It waits, with a real progress and never a timer, for what the next section needs. See `seams/` and `docs/design/design-system.md`.
- Something that follows a video runs on the compositor (a Web Animation), not in a frame loop. Long text and long lists use `content-visibility: auto` and are built in small slices.
- The long character pages (Vexana's and Guinevere's) hide the browser's scrollbar (`BareScrollbar`, `html[data-bare-scroll]` in `styles/base.css`), because a scrollbar that vanishes while the scroll is locked and returns after it moves the page sideways. The one progress mark is the hairline along the top of the screen (`components/hud/hud-frame.tsx`). Do not bring a scrollbar back on those pages.
- Judge speed on the production build, not `pnpm dev` (it is 2 to 3 times slower), with `scripts/perf/weak.mjs`.
- Effects are never gated on the device. If an effect costs too much, make it cheaper for everyone (transform and opacity, the compositor, `content-visibility`), do not turn it off on some devices.

## Logo

The logo is a vector (`components/logo/`, traced from the bitmap by `scripts/logo/build.py`). Use `AspirantLogo` wherever the logo appears. The letters are windows: the plate never covers them. The page transition (`components/curtain/`, `components/transition/`) zooms through those windows.

## Navbar and menu

The bar is sticky and always visible. Pages open from the full-screen menu (`components/nav/`), not from links in the bar. Each page has a pair of aspirants shown as art only, never with names, big on the empty left and right of the menu, where they stay (they do not follow the titles) and swap when another page is hovered. The menu art is built by `scripts/menu/build.py` so every figure has the same size, the eyes of both sit on one horizontal line, and no cut of the source shows (it fades out). If you add or change a portrait, rebuild with that script. The art is warmed after the site opens and is not part of the loading bar.

## Video

Use the custom player in `components/video-player/` (`VideoCard`) for new videos, not a bare `<video controls>`. Videos never start by themselves, with three exceptions. One: the story page (`/story`) plays its hero film muted and in a loop while it is on screen and not covered by the page that rises over it (it is paused otherwise, and held behind its still when it cannot play). Two: the chapter pages of the story (`/story/prologue`, `/story/chapter-NN`) play their title-card loop and the muted clips set in the text while they are on screen (a clip that kept its sound has a button; nothing plays with sound by itself). Three: Vexana's page plays some muted pictures by itself while they are on screen (the signature short, the Reel preview, the skin video of the Registry, the Craft clips, the cover film `final2`, the 3D process clip and the Guinevere dance), they pause when they leave the screen, and none has sound; the livestream also starts muted by itself while on screen and gets its sound when the visitor presses the sound button, and the game starts only when the visitor presses a button, and then plays with sound. Her page is built by `scripts/vexana/build.py` (see `docs/superpowers/specs/2026-10-24-vexana-page-design.md`). Guinevere's page (`features/character/guinevere/`) follows it: her files are made by `scripts/guinevere/build.py` (and `glow.py` for the second picture of her hero), the joins, the comic, the interactive drama and the 3D process are Vexana's own (`features/character/vexana/`), and the film, the second film and the heart dance are Vexana's files. Selena's page is built from recordings cut by `scripts/selena/build.py`, and Obsidia's by `scripts/obsidia/build.py` (both run on the engine in `features/character/stage/`): do not re-cut by hand, change the constants there and rebuild. The page picks the size that matches the visitor's display (width, height and pixel ratio, nothing else: the device and the connection never lower it) and loads that size (Selena's and Obsidia's pages wait before opening only for the welcome and the idle loop, and keep loading the rest in the background). While a page or a short waits for its frame the waiting video runs faster (the time skip in the stage engine). The videos have no sound (muted): sound is the music and the voice lines. Keep a video that plays beside the stage at 60 fps, since a 30 fps one makes the page pace at half rate.

Ruby's and Angela's pages are one pair on one view (`features/character/duo/`, routes `/character/ruby/` and `/character/angela/`): Ruby's is the night shift (a blueprint of her art shows through the pointer), Angela's is the first sunrise (a warmth map of hers). Their films are the site's own files in `public/video/ruby-angela/` (not encoded again, they play only when the visitor presses play); the second hero picture and the strip of stills are made by `scripts/ruby-angela/build.py` (the anaconda Python, Pillow and numpy).

Lesley's and Chang'e's pages are two ends of one channel (`features/character/lesley-change/`, routes `/character/lesley/` and `/character/change/`): Lesley's first screen is a scope that magnifies her splash art and fires a thread of light (hold to steady, let go to fire), Chang'e's is a bench with guides, pins that measure each other and markers on her gear. Both show their own splash art full bleed, share the order of the sections and a pill that leads to the other end, and use the site's own files in `public/video/lesley-change/` (they play only when the visitor presses play). Nothing is encoded for them: the sources hold no music, no cut-outs and no fan art for this pair.

## The story (`/story`) and About (`/about`)

`/story` is the story: a landing page (`features/story/landing/`) and the book, read one chapter to a page (`/story/prologue`, `/story/chapter-01` to `/story/chapter-48`, and `/story/the-end`; `features/story/reader/`). `/about` is the world explainer. The owner swapped the two on 1 Nov 2026 and `/experience` only redirects. On 3 Nov 2026 the owner replaced the old novel with the new one (`story/main.md` of the source folder) and asked for a heavily visual read: images, comic panels, film clips, voice lines and music in the right place of every scene. That reversed the plain-text rule of 1 Nov. Rules:

- The text, the visual scripts and the media all come from `scripts/story/` (`build.py`; see its README and `docs/superpowers/specs/2026-11-03-story-visual-reader-design.md`). Never edit `public/data/story/*`, `public/img/story/*` or `public/video/story/*` by hand: change the novel or a `scripts/story/visuals/cNN.json` and run `build.py`.
- A chapter page opens with a full-screen title card, then runs as one column of text on one plain colour (white, or the site's black; the visitor picks it in the reading settings, one theme for the whole story, no chapter changes it). Set between the paragraphs: wide stills, comic panels, muted clips, place shots and character cards. Voice players sit under the recorded lines and a music score runs under the chapter (only when site sound is on). Everything that moves is transform or opacity. One chapter is one page, never an infinite scroll, and the text is in the page's HTML at build time.
- Pictures illustrate the text and never add to it. Only official art, official comics and official films (the validator in `scripts/story/visuals.py` rejects fan art, cosplay, edits, gameplay, in-game animation and the live-action parody). A picture never shows a character or a reveal before the book does.
- A link to a chapter of the book is built only by `chapterHref` (`features/story/chapter-href.ts`). `storyChapterHref` is for the About page and the character pages, which still carry text from the older story: it maps an old chapter id to the nearest chapter of the book (`legacy-map.json`). Those pages need their own pass.
- The reader saves the place (`aspirants:reader`, versioned by the book, and `aspirants:prefs` `lastChapter`): keep both keys. `furthest` in `aspirants:reader` is the highest chapter reached and opens sealed pictures.
- The landing: Continue is the call when a place is saved, Start reading is the call for a fresh visitor, and the row never shows the wrong one first. The hero film is `scripts/story/hero.py`'s output and is waited for in the `/story` list. The join under the hero is Vexana's pair to interlude join (`features/story/landing/rise.tsx`): keep it a cover-up by the layout, with a snap after one second and no scroll cue inside it.
- The landing says nothing that gives the story away: the description and the cards use no `laterInStory` text, and a chapter picture that would reveal something is sealed (`spoiler` in its visual script) until the visitor has reached that chapter.

## The roster page (`/character`)

The wall of ten panels opens with a WebGL intro (`features/character/roster/intro/`, spec in `docs/design/roster-intro.md` and `roster-intro-engine.md`, reference recording in `docs/design/roster-reference/`). Rules:

- The intro plays only on a fresh load or when arriving from another page, never from `/character/*` (`lib/route-history.ts`). The page is black from the first paint (`RosterCover`); a skipped visit must never show black. Click, tap or Esc skips; no WebGL skips it; it must leave no running loop and a failsafe must never leave the page covered.
- Its chunk, stills and clips are in the `/character` loading list (`introItems()` in `lib/route-preloads.ts`). Only first-paint files go there.
- Geometry comes from `roster/layout.ts` (SLOTS, BOARD_H, SLASH, SEAMS). Do not hardcode positions in the engine. Do not put a `style` or a transform on `[data-roster-root]`.
- All ten panels, Obsidia and Selena too, are shaded until hovered. The background decoration (`roster/decor.tsx`) is minimal on purpose, the owner rejected a packed one: do not add to it.
- Specs that touch the roster use `skipGate` (it turns the intro off); `e2e/roster-intro.spec.ts` plays it on purpose. Compare with the recording using `scripts/roster-intro/compare.mjs`, check the black first paint with `scripts/roster-intro/first-paint.mjs`.

## Look and feel

Light mode by default (`data-theme="daybreak"`). Dark (`storm`) only where the story needs it. Modern, minimal, futuristic with a mechanical feel: generous spacing, thin lines, few effects, no glow or gradient clutter.

## Writing

Formal English written like to a friend but business. Short sentences. No em-dashes or en-dashes anywhere. No generic AI-sounding writing. "Aspirant power", never "conviction". Spell it Terrinia, Selrick, Storm Citadel. See `docs/design/canon-rules.md`.

## Workflow

- Run on `http://localhost:3000` (`pnpm dev`).
- Commit with conventional commits (headers under 100 characters) and push to `main` when done.
- Never list or mention Claude or any AI anywhere in this repository or its history: not as an author, co-author or contributor, and not in commit messages or trailers (no `Co-Authored-By`, no session links), pull requests, docs, code comments or file headers. A tool default that adds such a line is wrong here: leave it out.
- The site is served from the custom domain https://aspirant.cc (the domain root, no `/aspirant` path). The Pages workflow builds with an empty base path.
- `pnpm check` must pass before pushing: format, typecheck, lint, unit tests, knip.
